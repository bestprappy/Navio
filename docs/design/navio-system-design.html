Architecture v1.3 · current state

An EV-aware trip planner built as seven Spring apps behind one gateway.

Four domain services own their own schemas and never touch each other's tables. A Spring Cloud Gateway is the only application entry point, Keycloak is the only credential authority, and Kafka carries integration events only — written through a transactional outbox so a broker outage never blocks a commit.

01 — Runtime topology

How a request actually travels

Production ingress is NGINX → Spring Cloud Gateway → Eureka-resolved service. Development skips only the NGINX hop. The gateway holds no domain schema and no business authorization — every service re-validates the Keycloak JWT and enforces its own resource permissions.

04 — Data ownership

One database, seven walled schemas

A single PostgreSQL 16 + PostGIS instance keeps the 8 GB VM affordable, but each service connects with a database role scoped to the schemas it owns. Sharing an instance is an operational choice, not a licence to share tables.

SchemaOwnerHolds
iamUser ManagementProfiles, vehicles, suspensions, outbox
tripTrip PlanningTrips, permissions, revisions, outbox
evMobility & EVChargers, geo tiles, reviews, outbox
socialCommunityGroups, posts, votes, reports
notifCommunityNotifications, preferences, delivery log
mediaCommunityAssets and upload sessions
aiAI PlanningPrompts, sessions, usage, tool calls

Boundary rules

  • No cross-schema joins — and no cross-schema foreign keys, reads or writes.
  • No shared tables — Community never writes the trip schema, even for a trip attachment.
  • No resource roles in Keycloak — a trip-123-editor realm role would be unbounded.

What replaces them

  • Soft references — cross-domain IDs are validated through APIs or events, never FKs.
  • Disposable projections — a consumer's copy of a public trip is a cache, not a second authority.
  • Local authorization — the service that owns the resource owns the permission check.
  • Local search — Trip owns Explore search, Community owns post search, EV owns geo search. No Elasticsearch in v1.
05 — Messaging

The outbox is the source of truth, not Kafka

Kafka carries asynchronous integration events only — never logins, route calculations or AI streaming. One KRaft broker is not highly available, so the domain transaction must survive without it.

TopicProducerConsumersExamples
user.events.v1User ManagementTrip · Community · Mobility & EV UserRegistered · UserRoleChanged · UserSuspended
trip.events.v1Trip PlanningCommunity TripPublished · TripUpdated · TripDeleted · TripCopied
community.events.v1CommunityNotification / audit module PostCreated · CommentCreated · PostReported
mobility.events.v1Mobility & EVCommunity / admin consumers ChargerSubmitted · ChargerVerified · ChargerStatusChanged

Every event carries the same envelope: eventId · eventType · occurredAt · producer · partitionKey · traceId · payload. Votes never emit per-action events — only aggregate score snapshots, and only when another bounded context needs them.

06 — Observability

Mandatory, and deliberately not self-hosted in production

Logs, metrics and sampled traces all leave the VM through one Grafana Alloy collector. The full Grafana/Loki/Prometheus stack runs locally in Compose for development — the 8 GB application VM ships to a hosted backend instead.

1Emit

Structured JSON to stdout with service, environment, instance, request ID, trace ID and span ID. Actuator exposes health, liveness, readiness and Prometheus metrics.

2Collect

Grafana Alloy tails container and system logs, scrapes metrics and exports sampled OTLP traces. Local files are a short outage buffer only.

3Correlate

W3C trace context is propagated through NGINX, the gateway, REST calls, Kafka headers and AI tool calls, so one request ID stitches the whole path together.

Logs redact bearer tokens, passwords, cookies, database credentials and model-provider keys. Alerts watch HTTP latency and error rate, JVM and container resources, gateway failures, Eureka registrations, outbox backlog, Kafka consumer lag, provider failures and disk space.

07 — Failure behaviour

What still works when something breaks

The design rule is blunt: failure of AI or observability must never disable a core Navio workflow.

When this failsThe system does this
NGINXPublic ingress stops; the private gateway stays healthy and reachable internally.
Spring Cloud GatewayPublic APIs fail; domain services keep running privately.
Config ServerRunning services keep their loaded configuration; only new starts and refresh fail — and alert.
EurekaCached discovery works briefly; new registrations fail and alert.
KeycloakUnexpired JWTs keep working; new logins, refreshes and role changes fail.
KafkaTransactions still commit. Outbox rows queue up; projections and notifications lag.
Maps / charger providerServe cached or stale data, or return a controlled partial result.
AI Planning or OllamaAI endpoints degrade through the circuit breaker. All four core domains are unaffected.
Hosted observability backendTraffic continues; Alloy retries from bounded local buffers without blocking requests.
PostgreSQLStateful operations are unavailable. Alert and restore — this is the one hard single point of failure.
