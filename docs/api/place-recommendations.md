# Planner place recommendations

Implementation lives in the `feat/place-recommendations` client and trip-service worktrees. It is not deployed.

Each editable itinerary day shows a compact shadcn Accordion/Carousel shelf between Add a stop and its action buttons. Six destination-relevant candidates are shown at most. Popular candidates precede a deduplicated, mixed selection from the published destination Guide. Mixed shelves say Recommended places; a shelf containing only qualified popularity results says Popular with Navio travelers. Each candidate distinguishes Chosen by N travelers from Navio pick. Preview opens the normal place search preview; Add uses the existing visit mutation/autosave path and disables repeated additions in the same day. The larger guide shelf remains curated and is labeled accordingly.

`GET /v1/trips/{tripId}/place-recommendations?lat=...&lng=...` requires the trip owner's authenticated session. A bounded indexed query returns at most 48 canonical place IDs with at least five distinct eligible contributing accounts, ordered by count then ID. The search area is 50 km around that part of the day's destination, not the trip title. Private and public itineraries contribute equally, as explicitly requested by the user. One retained public place contributes once per account across all days/trips. Removing the final occurrence, deleting a trip or opting out withdraws that contribution on the next read. There are no increment-on-click counters, publication bonuses, guide-appearance votes or historic lifetime/trending claims.

My List, provider-independent personal saved locations, home/work anchors, residential address types, inherited `copied-item-*` stops and the dedicated Team sample owner are excluded. `navio.place-popularity.excluded-accounts` may add test/service account UUIDs; the Team owner is always excluded. Explicitly adding a new place to a copied plan creates an ordinary visit and qualifies normally. Old legacy Google IDs beginning ChI are normalized to GOOGLE: IDs. Provider namespaces stay separate; no heuristic cross-provider merging is attempted.

Private rows supply IDs and counts only. Candidate names, addresses and coordinates come from already published Guide content or active, explicitly Explore-listed public snapshots, with the same minimum sanitizer version as public readers. Unlisted/revoked snapshots do not supply metadata. Count-only IDs without public presentation data are not rendered. No private place names, notes, trip IDs, dates or account IDs enter the response. The threshold of five is a provisional product rule, not an anonymity guarantee or proof of worldwide popularity.

No Google discovery/detail/photo calls are added. The shelf observes already-fetched detail images in the existing in-memory query cache using a disabled `skipToken` observer; it cannot initiate a provider lookup. Otherwise a category thumbnail replaces the photo. Public-plan image URLs are deliberately not projected into this new shelf. No provider-content cache or new provider-data persistence is introduced. Public-place closure cannot be freshly verified without provider data; do not describe these suggestions as live availability.

`GET/PUT /v1/trips/place-popularity/preferences` reads/writes only the authenticated account's `{contributes:boolean}` preference. A missing preference defaults to true. The client exposes the control in Settings > Privacy > Place recommendations. Failed saves retain the saved switch value and produce the existing error toast. Aggregate responses have no-store headers; the browser shares requests for the same account/trip/coordinates with a 30-second freshness interval and invalidates them after a preference change. Other already-open browsers may retain their existing results until refetch. Recommendation failures fall back to Guide picks, while preference-load failures show Retry rather than an invented enabled state.

Rollout requires the Trip migration/service and client together. The feature checkout includes the banner-upload V30 from dev; popularity uses V31 and the V13 upgrade test expects 18 subsequent migrations. No production database or maintained sample content is changed by this implementation task.
